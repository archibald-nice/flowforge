## 5. 瓶颈分析

- **挂载 / 水合**：冷加载中位数从 100 → 300 为 316 ms → 626 ms（1.98×）。这部分随节点数近似线性抬升，更像初次挂载与媒体水合成本。
- **交互帧率**：拖拽 FPS 100 → 300 均为 ≈60.7（贴 vsync），主路径未因节点数掉帧。缩放/平移在 300 档出现 headless 空转偏高离群值，不能当成「更快」；有效信号仍是「没有掉到 60 以下」。
- **小地图**：开 60.7 (60.0–60.7) / 关 60.7 (60.7–60.7)，两者无差别，**不是** 300 档瓶颈。
- **IndexedDB / 保存**：中位数 808 → 845 ms，扣除 450ms 防抖后约 358 → 395 ms，随节点缓增，IndexedDB 不像主瓶颈。
- **堆**：JS 堆 100 → 300 为 16.3 → 45.2 MiB（2.77×），与节点 + `asset:` 媒体规模同向，是比交互帧率更明显的成本项。

## 6. 局限性

- **无 GPU**：Chromium 走软件渲染，绝对帧率明显低于有独显的机器；结论以相对伸缩性为主。
- **VM / 共享宿主**：`free -g` available 可能波动；本机 available < 4 GB 时按规则降档。
- **Headless**：无真实显示器合成；FPS 以 rAF 回调/秒换算，不是 presented-frame。Headless 常不锁 vsync，绝对值可能高于 60，只可作相对比较。
- **缩放路径**：产品关闭了 `zoomOnScroll`，本脚本用 Ctrl+滚轮（React Flow 激活键）做 20 次缩放。
- **绝对值不可跨机比较**。
- **绕过**：本次**没有**把 `asset:` 改写成 `simulated:`，也没有对 IndexedDB 做 harness 迁移。
